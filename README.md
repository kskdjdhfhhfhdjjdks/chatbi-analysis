# ChatBI · 对话式智能问数

> 用业务语言直接提问，系统自动完成 **语义理解 → SQL 生成 → 安全校验 → 查询执行 → 可视化与归因下钻** 全链路。

一个支持 **DeepSeek 语义解析 + 可验证数据计算** 的 ChatBI 演示项目。内置 202,500 行 SaaS 增长模拟数据，通过服务端代理调用模型；未配置 Key 时可使用离线规则模式。当前 SQL 用于展示，实际结果在浏览器内聚合计算。

**本地运行**：`npm install`，复制 `.env.example` 为 `.env` 并填写 `DEEPSEEK_API_KEY`，再执行 `npm run dev`。详细接入说明见文末。

详细架构、问题分析和本轮改动见 [项目理解与优化记录](docs/PROJECT_REVIEW.md)。

# 一、这个 Demo 想证明什么

一句话：**把「不可信」的地方全部替换成「可验证」的机制。**

| 常见做法 | 本项目做法 |
| --- | --- |
| 模型自由生成 SQL | 语义层先归一化，再用**指标元数据**约束聚合方式（比率型强制 `SUM(分子)/SUM(分母)`） |
| 口径模糊时猜一个 | **主动澄清**（「留存」→ 反问 D1/D7/D30） |
| 主观问题直接编建议 | **MECE 拆解**成可执行子问题，基于客观数据合成结论 |
| 只测「能不能答对」 | **双向验证**：既测该拦的拦住了，也测不该拦的放过了 |
| 只展示成功的用例 | 公开预置标注评分与未修复 Badcase；静态评分不代表当前 DeepSeek 的实测效果 |

# 二、MECE 子问题拆解（核心差异化）

这是我认为整个项目最有产品价值的设计。

## 问题

用户问「**哪些渠道值得加投**」，这是典型的**主观决策问题**。它没有对应的指标，也没有对应的 SQL——你没法写一条 SQL 查出"值不值得"。

**大多数 NL2SQL 系统在这里会失败**：要么返回澄清卡片（"没听懂"），要么让大模型直接编一段听起来很有道理的建议。后者更危险，因为**它的输出无法被验证**。

## 设计

按 MECE 原则（相互独立、完全穷尽），把主观问题翻译成**一棵确定性子问题树**，每个子问题都是一次可执行的取数：

```
「哪些渠道值得加投」
├── ① 回报水平：各渠道 LTV/CAC        ← 决定「值不值得投」
├── ② 获客效率：各渠道 CAC            ← 决定「能不能规模化投」
├── ③ 用户质量：各渠道 LTV            ← 识别被单一 CAC 误导的渠道
└── ④ 变化趋势：各渠道 CAC 近30天趋势  ← 排除「正在恶化」的渠道
```

然后**基于客观数据合成结论**。比如 ROI 按中位数分层：≥1.15× 中位数 → 建议加投；0.85~1.15× → 维持观察；<0.85× → 建议收缩。同时叠加趋势判断，正在恶化的渠道即使当前 ROI 尚可也标记为收缩。

## 为什么这么设计

| 设计选择 | 理由 |
| --- | --- |
| **不直接回答主观问题** | 主观问题的答案无法验证，模型只能编 |
| **拆成确定性取数** | 每个子问题都能对应到一条可执行、可复现的 SQL |
| **四视角而非单指标** | 单一 ROI 会漏掉「便宜但低质」的渠道，必须交叉验证 |
| **加趋势视角** | 静态快照会掩盖恶化中的渠道，效率下滑说明流量竞争在加剧 |
| **建议分层而非给一个结论** | 决策需要的是分层依据，不是一个"该/不该"的二值答案 |

**产品价值**：把「AI 给建议」这个不可信的过程，替换成了「AI 给依据 + 依据可追溯」的可信过程。界面上完整展示了拆解思路、每个子问题的取数依据、以及综合结论——**用户可以自己判断这个建议靠不靠谱**。

首版覆盖三类高频策略问法：**渠道投放决策**、**业务健康度体检**、**留存提升路径诊断**。

## 已知边界

- 只覆盖三类模板，未命中模板的策略问题会退回澄清引导（这是有意的——**明确暴露能力边界比假装什么都能答更好**）
- 子问题的视角是预定义的，尚未做到让模型动态生成拆解维度
- 属于 BC-008 的修复成果，已沉淀为回归用例

## 数据设计要点

事实表为 `天 × 渠道 × 设备 × 地区 × 套餐 × 用户分层` 的笛卡尔积，共 **202,500 行**，由确定性伪随机数生成，每次刷新结果一致。

三个关键工程细节：

1. **单格基数必须够大**。全维度组合下每格样本很小，`Math.round` 会把新增/留存这类小数值抹平成 0，导致比率失真（曾出现「7日留存率 0.59%」的错误）。解决方案是放大基数，用 `Math.sqrt` 派生 MAU 避免比率系统性偏移。

2. **比率型指标必须饱和压缩**。付费率由「渠道 × 套餐 × 地区 × 分层」四个因子连乘会轻易突破 100%，因此用幂函数压缩到 `(0, 1)`，最终产出 免费版 21% → 专业版 48% → 企业版 62% 的合理阶梯。

3. **派生指标要有真实漂移**。用户粘性（DAU/MAU）如果完全由 DAU 派生，比值会退化成常量，趋势图是一条直线，看起来像 bug。给月活池加入独立的累积效应后，粘性才呈现真实的缓慢下行趋势。

数据中内置三类异常用于演示：Android 端因付费广告停投而下滑、企业版留存异常走低、iOS 端崩溃率走高。

## 比率型指标的正确聚合

这是最常见的 SQL 错误来源，项目中通过指标元数据强制约束：

```sql
-- ❌ 错误：行级相除再平均
AVG(revenue / marketing_cost)

-- ✅ 正确：先分别求和再相除
SUM(marketing_cost) / NULLIF(SUM(new_users), 0)
```

## 上下文感知的追问建议

每轮回答后的追问按钮不是固定列表，而是根据当前上下文动态生成并排序。六条策略：

1. **排除法**：已经拆过的维度不再推荐
2. **分析链路推进**：看完获客成本，下一步推 LTV/CAC
3. **指标类型判断**：比率型优先推趋势，绝对值优先推对比
4. **避免重复展示**：已给出归因面板时不再推归因
5. **定向建议**：结合已识别的维度值推荐下一步
6. **策略视角升级**：单指标问数结束后，提示可切到 MECE 策略视角

每条建议都附带推荐理由，界面上首条直接展示理由、其余悬浮可见。

# 五、工程化：可验证性

> 这个项目的一个特点：**所有关键数据都被断言保护**，改坏了会立刻失败。

```bash
npm run check     # 类型检查 + 全部验证套件
npm run verify    # 只跑验证套件
```

验证套件共 9 组，全部用项目自带的 rolldown 打包执行，**不引入任何测试框架依赖**：

| 套件 | 保障什么 |
| --- | --- |
| `security` | 安全机制**双向**用例：20 条恶意输入必须拦住 + 31 条正常问法必须放行 |
| `regress` | 问法路由回归：18 类问法分发到正确意图 |
| `consistency` | 数据自洽：评测卡片数字 = 趋势图终点、指标在合理区间、统计文案跟随数据、版本记录单调收敛 |
| `render` | 组件渲染：MECE 面板的关键文案真的落到 DOM 里，无 `undefined`/`NaN` |
| `suggest` | 追问建议：元数据引用有效、上下文感知生效、排序去重契约 |
| `llm` | 模型计划类型、日期、安全覆盖、多序列趋势、筛选继承 |
| `api` | 客户端到代理到模拟上游的完整请求链路、密钥隔离、限流和异常 |
| `demo` | 演示动线：README 里列出的每个问题都能跑通 |
| `deploy` | 部署前置检查：Netlify 配置完整性、`vite base` 白屏排查、产物引用与仓库卫生 |

**为什么要做这个**：多环节链路最典型的失控方式是「改一处、坏一处，而自己不知道」。这套断言让每次改动后都能立刻确认没有回归——`security` 套件的双向用例就是这么抓出「黑名单误拦 `ORDER BY ... DESC`」这个 bug 的（详见安全页面的「设计权衡」章节）。

# 六、说明

本项目使用内置模拟数据集，不连接真实数据库。模型负责将问题翻译成受约束的查询计划，程序负责校验和计算；MECE 拆解仍使用预定义模板，并在「处理链路透视」中把每一步的处理结果与耗时透明化展示。

> **一句话总结**：这个项目里，凡是「模型可能编」的地方，我都换成了一套「可验证的机制」。

# 七、DeepSeek 接入与部署

## 本地启动

使用 Node 22.12+ 或 Node 24：

```powershell
npm install
Copy-Item .env.example .env
```

在本地编辑 `.env`：

```dotenv
DEEPSEEK_API_KEY=你的真实密钥
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-flash
```

```powershell
npm run dev
```

打开终端输出的本地地址。底部显示“已配置”仅表示服务端有密钥，不代表鉴权和额度已验证；发送一个问题后，回答下方应出现“大模型语义解析”与模型名称。未配置 Key、网络失败或非法模型计划会明确标注规则降级。

密钥只能放服务端环境变量，不要使用 `VITE_` 前缀，不要填写到聊天输入框或提交 Git。修改 `.env` 或函数代码后重启开发服务器，再点“重新检测”。

当前模型名称与 JSON 输出协议参照 [DeepSeek 首次调用文档](https://api-docs.deepseek.com/) 和 [JSON Output 文档](https://api-docs.deepseek.com/guides/json_mode/)。模型名称可通过环境变量调整。

## 建议的演示顺序

## 部署到 Netlify

1. 将代码提交并 `git push` 到自己的 GitHub 仓库。
2. 在 Netlify 导入仓库，使用 `netlify.toml` 的 `npm run build` 和 `dist` 配置。
3. 在 Netlify 的环境变量中设置 `DEEPSEEK_API_KEY`，可选设置 `DEEPSEEK_MODEL` 和 `DEEPSEEK_BASE_URL`；变量需要在 Functions 运行时可用。
4. 重新部署，验证 `/api/chat` 的 GET 返回 JSON 配置状态，再在页面发送真实问数问题。

`netlify.toml` 配置了 Functions 目录和 `/api/chat` 重写，必须放在 SPA 兜底之前。Vite 本地开发复用相同函数。`npm run preview` 只预览静态产物，不提供模型代理；仅上传 `dist/` 的静态托管也不包含函数，请使用支持 Functions 的部署流程。

当前 API 使用进程内限流（每 IP 每 10 分钟 30 次），不同 Serverless 实例不共享配额。正式公开使用需增加平台配额和调用监控；当前不支持真实数据库连接、任意 SQL、预测和任意派生指标。
